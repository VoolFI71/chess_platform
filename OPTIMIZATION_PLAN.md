# План оптимизации задержки ходов в шахматной партии

## 🔍 Анализ текущих узких мест

### Backend (сервер)

1. **Лишние запросы к БД:**
   - `expire_all()` перед каждым ходом - сбрасывает весь кэш
   - `_compute_effective_clocks` делает запрос для получения последнего хода
   - `_compute_elapsed_ms` делает запрос для получения последнего хода
   - `get_moves` после хода для отправки через WebSocket (можно оптимизировать)
   - `db.refresh` дважды (game и move) - можно объединить
   - `cancel_auto_cancel` делает отдельный запрос к БД

2. **Логирование:**
   - `LOGGER.info` на каждый ход - может замедлять

3. **Вычисление времени:**
   - Два метода делают одинаковый запрос к БД для получения последнего хода

### Frontend (клиент)

1. **Дублирование вычислений:**
   - Два вызова `getDisplayedClocks` (один с applyRunning=true, другой с false)
   - Можно оптимизировать, вызвав один раз

2. **Лишние перерисовки:**
   - `renderBoard()` вызывается несколько раз
   - `updateLegalMoves()` вызывается после каждого хода

3. **Синхронные операции:**
   - `JSON.stringify` может быть медленным для больших payloads

## 🚀 Оптимизации (по приоритету)

### Приоритет 1: Критичные оптимизации (быстрый эффект)

#### 1.1 Оптимизация запросов к БД на backend

**Проблема:** Два метода (`_compute_effective_clocks` и `_compute_elapsed_ms`) делают одинаковый запрос для получения последнего хода.

**Решение:**
- Кэшировать последний ход в методе `make_move`
- Передавать его в методы вычисления времени
- Использовать `joinedload` для загрузки последнего хода вместе с игрой

**Ожидаемый эффект:** -20-30мс на ход

#### 1.2 Убрать лишние `db.refresh`

**Проблема:** После хода вызывается `db.refresh` дважды (для game и move).

**Решение:**
- Использовать `db.refresh` только для game (move уже в сессии)
- Или использовать `returning` в SQLAlchemy для получения обновленных данных

**Ожидаемый эффект:** -5-10мс на ход

#### 1.3 Оптимизация `get_moves` после хода

**Проблема:** После хода загружаются все последние ходы для отправки через WebSocket.

**Решение:**
- Не загружать все ходы, если они уже есть в памяти
- Использовать кэш последних ходов
- Отправлять только новый ход, а не все ходы

**Ожидаемый эффект:** -10-20мс на ход

#### 1.4 Оптимизация `cancel_auto_cancel`

**Проблема:** `cancel_auto_cancel` делает отдельный запрос к БД.

**Решение:**
- Выполнять отмену в той же транзакции
- Или делать асинхронно после коммита

**Ожидаемый эффект:** -5-10мс на ход

### Приоритет 2: Важные оптимизации

#### 2.1 Оптимизация вычисления времени на клиенте

**Проблема:** Два вызова `getDisplayedClocks` (один с applyRunning=true, другой с false).

**Решение:**
```javascript
// Было:
const clocks = getDisplayedClocks(true);
const opponentClocks = getDisplayedClocks(false);

// Стало:
const clocks = getDisplayedClocks(true);
const opponentClocks = { 
  white: state.game.white_clock_ms, 
  black: state.game.black_clock_ms 
};
```

**Ожидаемый эффект:** -1-2мс на ход

#### 2.2 Оптимизация перерисовки UI

**Проблема:** `renderBoard()` вызывается несколько раз.

**Решение:**
- Использовать `requestAnimationFrame` для батчинга обновлений
- Дебаунсить обновления UI
- Обновлять только измененные части

**Ожидаемый эффект:** -5-10мс на ход (воспринимаемая задержка)

#### 2.3 Убрать `expire_all()` перед ходом

**Проблема:** `expire_all()` сбрасывает весь кэш сессии перед каждым ходом.

**Решение:**
- Использовать `expire` только для конкретного объекта Game
- Или использовать `with_for_update()` без expire_all

**Ожидаемый эффект:** -5-10мс на ход

### Приоритет 3: Дополнительные оптимизации

#### 3.1 Оптимизация логирования

**Проблема:** `LOGGER.info` на каждый ход может замедлять.

**Решение:**
- Использовать асинхронное логирование
- Или логировать только важные события
- Использовать уровень DEBUG для детального логирования

**Ожидаемый эффект:** -2-5мс на ход

#### 3.2 Оптимизация WebSocket payload

**Проблема:** Отправляется полный `GameDetail` с всеми ходами.

**Решение:**
- Отправлять только измененные данные (delta updates)
- Использовать бинарный протокол вместо JSON
- Сжимать payload для больших игр

**Ожидаемый эффект:** -5-15мс на ход (зависит от размера payload)

#### 3.3 Оптимизация валидации хода

**Проблема:** Валидация хода на клиенте может быть медленной.

**Решение:**
- Кэшировать результаты валидации
- Использовать Web Workers для валидации
- Оптимизировать алгоритм проверки легальности ходов

**Ожидаемый эффект:** -1-3мс на ход

### 1. Кэширование последнего хода

```python
async def make_move(...):
    # Загружаем последний ход один раз
    last_move = await self._get_last_move_cached(game_id)
    
    # Используем его в вычислениях
    elapsed_ms = self._compute_elapsed_ms_from_move(last_move)
    effective_clocks = self._compute_effective_clocks_from_move(game, last_move)
```

### 2. Оптимизация `get_moves`

```python
# Вместо загрузки всех ходов, отправляем только новый
# Или используем кэш последних ходов
if hasattr(self, '_moves_cache'):
    self._moves_cache.append(move)
else:
    moves = await self.get_moves(game_id, limit=RECENT_MOVES_LIMIT)
```

### 3. Оптимизация перерисовки UI

```javascript
// Использовать requestAnimationFrame для батчинга
let renderScheduled = false;
function scheduleRender() {
  if (!renderScheduled) {
    renderScheduled = true;

      renderBoard();
      updateClockDisplays();
      renderScheduled = false;
    });
```

## ⚠️ Важные замечания

1. **Не жертвовать надежностью ради скорости** - оптимизации не должны нарушать корректность
2. **Тестировать после каждой оптимизации** - убедиться, что ничего не сломалось
3. **Мониторить производительность** - измерять эффект от каждой оптимизации
4. **Учитывать нагрузку** - некоторые оптимизации могут увеличить нагрузку на память
