# План миграции games_service на Golang

## Обзор

Микросервис `games_service` отвечает за управление шахматными партиями, включая:
- Создание и управление играми
- Обработку ходов и валидацию
- Управление таймерами
- WebSocket соединения для real-time обновлений
- Фоновые задачи (watchdog для таймаутов)
- Статистику игр

## Текущая архитектура (Python/FastAPI)

### Зависимости
- **FastAPI** - HTTP/WebSocket сервер
- **SQLAlchemy** (async) - ORM для PostgreSQL
- **python-chess** - библиотека для работы с шахматами
- **psycopg2/asyncpg** - драйверы PostgreSQL
- **alembic** - миграции БД
- **prometheus-fastapi-instrumentator** - метрики

### Основные компоненты
1. **HTTP роутеры** (`routers/games.py`, `routers/internal.py`)
2. **WebSocket роутер** (`routers/game_ws.py`)
3. **Бизнес-логика** (`services/games.py` - ~1200 строк)
4. **Модели данных** (`models/game.py`, `models/move.py`)
5. **Схемы валидации** (`schemas/game.py`, `schemas/stats.py`)
6. **WebSocket менеджер** (`realtime/manager.py`)
7. **Watchdog** (`watchdog.py`) - фоновые задачи

#### 1.2 Выбор библиотек Go
- **HTTP/WebSocket**: `github.com/gin-gonic/gin` или `github.com/gofiber/fiber` (легче) или стандартный `net/http` + `github.com/gorilla/websocket`
- **ORM**: `gorm.io/gorm` (синхронный) или `github.com/jackc/pgx/v5` (async, ближе к asyncpg)
- **Миграции**: `github.com/golang-migrate/migrate` или использовать существующие SQL файлы
- **Валидация**: `github.com/go-playground/validator` или встроенные теги
- **Шахматы**: портировать логику из `python-chess` или использовать `github.com/notnil/chess`
- **Конфигурация**: `github.com/spf13/viper` или стандартные env переменные
- **Логирование**: `github.com/sirupsen/logrus` или стандартный `log/slog`
- **Метрики**: `github.com/prometheus/client_golang`
- **JWT**: `github.com/golang-jwt/jwt/v5`

**Рекомендация**: Использовать `pgx/v5` с пулом соединений для async операций, `gin` для HTTP, `gorilla/websocket` для WebSocket.

### Этап 2: Миграция моделей и схем (2-3 дня)

#### 2.1 Модели данных
- Портировать SQLAlchemy модели в GORM структуры или использовать `pgx` с ручными запросами
- Сохранить совместимость с существующей схемой БД
- Использовать теги для валидации и маппинга

```go
type Game struct {
    ID                uuid.UUID  `gorm:"type:uuid;primary_key;default:gen_random_uuid()"`
    WhiteID           *int       `gorm:"index"`
    BlackID           *int       `gorm:"index"`
    InitialPos        string     `gorm:"type:text;not null;default:'startpos'"`
    CurrentPos        string     `gorm:"type:text;not null"`
    NextTurn          string     `gorm:"type:text;not null;default:'w'"`
    TimeControl       *datatypes.JSON `gorm:"type:jsonb"`
    MoveCount         int        `gorm:"not null;default:0"`
    Status            string     `gorm:"type:text;not null;default:'CREATED';index"`
    WhiteClockMs      int64      `gorm:"type:bigint;not null;default:0"`
    BlackClockMs      int64      `gorm:"type:bigint;not null;default:0"`
    Result            *string    `gorm:"type:text"`
    TerminationReason *string    `gorm:"type:text"`
    EndedBy           *int
    PGN               *string    `gorm:"type:text"`
    MetadataJSON      *datatypes.JSON `gorm:"type:jsonb;column:metadata"`
    CreatedAt         time.Time  `gorm:"type:timestamptz;not null;default:now()"`
    StartedAt         *time.Time `gorm:"type:timestamptz"`
    FinishedAt        *time.Time `gorm:"type:timestamptz"`
    
    Moves     []Move         `gorm:"foreignKey:GameID;constraint:OnDelete:CASCADE"`
    Snapshots []GameSnapshot `gorm:"foreignKey:GameID;constraint:OnDelete:CASCADE"`
}
```

#### 2.2 Схемы валидации (DTO)
- Создать структуры для запросов/ответов
- Использовать теги `validate` для валидации
- JSON теги для сериализации

### Этап 3: Портирование шахматной логики (3-4 дня)

#### 3.1 Библиотека для шахмат
**Варианты:**
1. Использовать `github.com/notnil/chess` - готовая библиотека
2. Портировать логику из `python-chess` - больше контроля

**Рекомендация**: Использовать `notnil/chess`, но проверить совместимость с текущей логикой.

#### 3.2 Ключевые функции для портирования
- Валидация ходов (UCI формат)
- Проверка мата/пата/ничьей
- Генерация PGN
- Работа с FEN позициями
- Проверка легальности ходов

### Этап 4: Миграция бизнес-логики (5-7 дней)

#### 4.1 GameService
Портировать основные методы:
- `create_game` - создание игры
- `get_game_with_moves` - получение игры с ходами
- `make_move` - обработка хода
- `resign` - сдача
- `timeout` - обработка таймаута
- `_compute_clocks_for_move` - расчет таймеров
- `_compute_effective_clocks` - эффективное время
- `build_game_detail` - построение детальной информации
- `build_game_summary` - построение краткой информации

#### 4.2 Особенности портирования
- **Асинхронность**: Go использует горутины вместо async/await
- **Контексты**: Использовать `context.Context` для отмены операций
- **Ошибки**: Использовать стандартные Go ошибки вместо исключений
- **Транзакции**: Использовать транзакции БД через `pgx`

### Этап 5: HTTP роутеры (2-3 дня)

#### 5.1 Основные эндпоинты
- `POST /api/games` - создать игру
- `GET /api/games/{game_id}` - получить игру
- `POST /api/games/{game_id}/move` - сделать ход
- `POST /api/games/{game_id}/resign` - сдаться
- `POST /api/games/{game_id}/timeout` - объявить таймаут
- `GET /api/games/{game_id}/moves` - список ходов
- `GET /api/games` - список игр (с фильтрацией)

#### 5.2 Internal эндпоинты
- `GET /internal/stats/{user_id}` - статистика пользователя
- `GET /internal/games/{game_id}` - внутренний доступ к игре

#### 5.3 Middleware
- Аутентификация (JWT)
- Логирование
- Метрики Prometheus
- GZip сжатие
- CORS (если нужно)

### Этап 6: WebSocket реализация (3-4 дня)

#### 6.1 WebSocket менеджер
Портировать `GameConnectionManager`:
- Управление соединениями по `game_id`
- Broadcast сообщений всем подписчикам игры
- Персональные сообщения
- Обработка отключений

#### 6.2 WebSocket обработчик
- Прием соединений
- Аутентификация через токен в query параметре
- Обработка сообщений (make_move, resign и т.д.)
- Отправка обновлений состояния

**Особенности Go:**
- Использовать `gorilla/websocket` или стандартный `net/http` с upgrade
- Горутины для каждого соединения
- Каналы для коммуникации между горутинами

## Технические детали

### База данных
- **Подход**: Использовать `pgx/v5` с пулом соединений
- **Миграции**: Использовать существующие SQL файлы или `golang-migrate`
- **Транзакции**: Явное управление транзакциями через `pgx`

### Асинхронность
- **HTTP**: Стандартный `net/http` с горутинами (автоматически)
- **WebSocket**: Горутина на каждое соединение
- **Watchdog**: Отдельная горутина с `time.Ticker`
- **БД**: Использовать `pgx` с async операциями

### Обработка ошибок
- Использовать стандартные Go ошибки
- Обертки ошибок с контекстом (`fmt.Errorf`)
- Логирование ошибок с уровнем severity

### Логирование
- Структурированное логирование (`logrus` или `slog`)
- Уровни логирования (DEBUG, INFO, WARN, ERROR)
- Контекст в логах (request_id, game_id и т.д.)

### Метрики
- Prometheus метрики
- HTTP метрики (latency, requests/sec)
- WebSocket метрики (connections, messages/sec)
- БД метрики (query time, pool size)

## Преимущества миграции на Go

1. **Производительность**: 
   - Лучшая производительность для concurrent операций
   - Меньше использование памяти
   - Быстрее обработка WebSocket соединений

2. **Простота деплоя**:
   - Один бинарный файл
   - Нет зависимостей от интерпретатора
   - Быстрый старт

3. **Типизация**:
   - Статическая типизация снижает ошибки
   - Лучшая поддержка IDE
   - Компилятор находит ошибки до runtime

4. **Concurrency**:
   - Нативная поддержка горутин
   - Эффективная работа с тысячами WebSocket соединений

## Рекомендации

1. **Начать с простых частей**: Сначала портировать модели и простые HTTP эндпоинты
