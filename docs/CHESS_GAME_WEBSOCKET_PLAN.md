# План реализации шахматной партии на WebSocket между игроками

## Обзор архитектуры

Система реализует шахматную партию в реальном времени между двумя игроками через WebSocket соединения. Backend обрабатывает валидацию ходов, управление временем, синхронизацию состояния и широковещательную рассылку обновлений всем подключенным клиентам.

## Компоненты системы

### 1. Backend компоненты

#### 1.1. WebSocket Router (`game_ws.py`)
**Назначение**: Обработка WebSocket соединений и маршрутизация сообщений

**Функционал**:
- Прием WebSocket подключений по пути `/ws/games/{game_id}`
- Аутентификация через JWT токен в query параметре
- Определение роли пользователя (white/black/viewer)
- Обработка входящих сообщений от клиентов
- Отправка ответов и широковещательных сообщений

**Текущая реализация**:
- ✅ Подключение/отключение клиентов
- ✅ Аутентификация через токен
- ✅ Обработка ходов (`make_move`)
- ✅ Отправка начального состояния (`state`)
- ✅ Широковещательная рассылка ходов (`move_made`)
- ✅ Обработка ошибок и отклоненных ходов

#### 1.2. Game Service (`games.py`)
**Назначение**: Бизнес-логика игры

**Функционал**:
- Создание игры
- Присоединение игроков
- Валидация и выполнение ходов
- Управление временем (таймеры)
- Определение окончания игры (мат, пат, таймаут, сдача)
- Обновление рейтингов

**Текущая реализация**:
- ✅ Создание игры с начальной позицией (FEN)
- ✅ Присоединение второго игрока
- ✅ Валидация ходов через библиотеку `chess`
- ✅ Вычисление времени с учетом инкремента
- ✅ Проверка окончания игры (мат, пат, недостаточно материала)
- ✅ Обновление рейтингов Elo
- ✅ Автоотмена игры при отсутствии первого хода

#### 1.3. WebSocket Manager (`realtime/manager.py`)
**Назначение**: Управление активными WebSocket соединениями

**Функционал**:
- Хранение активных соединений по game_id
- Широковещательная рассылка сообщений всем подключенным клиентам
- Отправка персональных сообщений
- Автоматическая очистка разорванных соединений

**Текущая реализация**:
- ✅ Хранение соединений в словаре `{game_id: {websocket: ConnectionInfo}}`
- ✅ Thread-safe операции через `asyncio.Lock`
- ✅ Автоматическая очистка при ошибках отправки

#### 1.4. Модели данных
**Game Model** (`models/game.py`):
- Хранение состояния игры (FEN, ход, статус)
- Время игроков (white_clock_ms, black_clock_ms)
- Метаданные (time_control, metadata_json)
- Связь с ходами (moves relationship)

**Move Model** (`models/move.py`):
- Хранение каждого хода (UCI, SAN, FEN после хода)
- Время после хода (clocks_after)
- Индекс хода для восстановления позиции

**Schemas** (`schemas/game.py`):
- Pydantic модели для валидации входящих данных
- Сериализация для WebSocket сообщений

### 2. Протокол WebSocket

#### 2.1. Подключение
```
ws://host/ws/games/{game_id}?token={jwt_token}
```

**Процесс подключения**:
1. Клиент устанавливает WebSocket соединение
2. Сервер проверяет JWT токен
3. Сервер загружает игру и последние ходы
4. Сервер определяет роль пользователя (white/black/viewer)
5. Сервер отправляет начальное состояние (`state`)

#### 2.2. Типы сообщений

**От клиента к серверу**:
```json
{
  "type": "make_move",
  "uci": "e2e4",
  "promotion": null,
  "white_clock_ms": 295000,
  "black_clock_ms": 300000,
  "client_move_id": "web-1234567890"
}
```

**От сервера к клиенту**:

1. **state** - начальное состояние при подключении:
```json
{
  "type": "state",
  "game": {
    "id": "uuid",
    "white_id": 1,
    "black_id": 2,
    "status": "ACTIVE",
    "next_turn": "w",
    "current_pos": "rnbqkbnr/pppppppp/8/8/4P3/8/PPPP1PPP/RNBQKBNR b KQkq e3 0 1",
    "white_clock_ms": 300000,
    "black_clock_ms": 300000,
    "moves": [...]
  }
}
```

2. **move_made** - ход выполнен:
```json
{
  "type": "move_made",
  "client_move_id": "web-1234567890",
  "move": {
    "id": 42,
    "uci": "e2e4",
    "san": "e4",
    "fen_after": "...",
    "move_index": 1,
    "created_at": "2024-01-01T12:00:00Z"
  },
  "game": {
    "next_turn": "b",
    "white_clock_ms": 300000,
    "black_clock_ms": 300000,
    ...
  }
}
```

3. **move_rejected** - ход отклонен:
```json
{
  "type": "move_rejected",
  "message": "Недопустимый ход",
  "client_move_id": "web-1234567890"
}
```

4. **game_finished** - игра завершена:
```json
{
  "type": "game_finished",
  "game": {
    "status": "FINISHED",
    "result": "1-0",
    "termination_reason": "CHECKMATE",
    ...
  }
}
```

5. **game_cancelled** - игра отменена:
```json
{
  "type": "game_cancelled",
  "game_id": "uuid"
}
```

### 3. Обработка ходов

#### 3.1. Процесс выполнения хода

1. **Клиент отправляет ход**:
   - Вычисляет текущее время с учетом прошедшего времени
   - Отправляет UCI ход и время обоих игроков

2. **Сервер валидирует ход**:
   - Проверяет, что игра активна
   - Проверяет, что оба игрока присоединились
   - Проверяет, что очередь правильного игрока
   - Проверяет, что ход легален (через библиотеку `chess`)
   - Проверяет таймаут (время не истекло)

3. **Сервер выполняет ход**:
   - Применяет ход к доске
   - Вычисляет новое время (вычитает прошедшее время, добавляет инкремент)
   - Сохраняет ход в БД
   - Обновляет состояние игры
   - Проверяет окончание игры (мат, пат, ничья)

4. **Сервер рассылает обновление**:
   - Отправляет `move_made` всем подключенным клиентам
   - Если игра завершена, отправляет `game_finished`

#### 3.2. Управление временем

**Логика времени**:
- Время хранится в миллисекундах в БД
- Клиент отслеживает прошедшее время локально
- При отправке хода клиент вычитает прошедшее время
- Сервер проверяет время и может пересчитать при необходимости
- После хода добавляется инкремент (если настроен)

**Особенности**:
- Первый ход: время не вычитается (дается 30 секунд на первый ход)
- Последующие ходы: время вычитается + добавляется инкремент
- Таймаут проверяется на сервере перед принятием хода

### 4. Безопасность

#### 4.1. Аутентификация
- JWT токен в query параметре WebSocket URL
- Проверка токена при подключении
- Закрытие соединения при невалидном токене (код 4401)

#### 4.2. Авторизация
- Проверка роли пользователя (white/black/viewer)
- Только участники могут делать ходы
- Проверка очереди хода (next_turn)

#### 4.3. Валидация ходов
- Проверка легальности хода через библиотеку `chess`
- Проверка формата UCI
- Проверка времени (не истекло ли)
- Проверка статуса игры (активна ли)

#### 4.4. Защита от атак
- Rate limiting (можно добавить)
- Валидация всех входящих данных через Pydantic
- SQL injection защита через SQLAlchemy ORM
- Блокировка строк БД при обновлении (SELECT FOR UPDATE)

### 5. Обработка ошибок

#### 5.1. Ошибки подключения
- Невалидный токен → закрытие с кодом 4401
- Игра не найдена → закрытие с кодом 4404
- Недостаточно прав → закрытие соединения

#### 5.2. Ошибки ходов
- Недопустимый ход → `move_rejected`
- Не ваша очередь → `move_rejected`
- Время истекло → `move_rejected`
- Игра завершена → `move_rejected`

#### 5.3. Ошибки сети
- Разрыв соединения → автоматическая очистка из менеджера
- Ошибка отправки → удаление соединения из списка
- Таймаут → автоматическое переподключение на клиенте

### 6. Масштабируемость

#### 6.1. Текущие ограничения
- WebSocket менеджер хранит соединения в памяти
- Не поддерживает горизонтальное масштабирование (несколько инстансов)
- Нет распределенного кэширования

#### 6.2. Возможные улучшения

**Горизонтальное масштабирование**:
- Использование Redis Pub/Sub для рассылки между инстансами
- Sticky sessions через load balancer
- Или использование специализированных сервисов (Socket.IO с Redis adapter)

**Оптимизация БД**:
- Индексы на часто используемые поля (game_id, status, created_at)
- Снапшоты позиций каждые N ходов (уже реализовано)
- Партиционирование таблицы moves по game_id

**Кэширование**:
- Кэширование активных игр в Redis
- Кэширование последних ходов
- Кэширование легальных ходов для позиции
