# Анализ архитектуры информационной системы ChessMint методом чёрного ящика

## Цель

Исследовать архитектуру онлайн-шахматной платформы ChessMint методом чёрного ящика, провести оценку эффективности архитектуры и представить рекомендации по дальнейшему совершенствованию.

---

## Ход выполнения задания

### 1. Исследование внешнего функционала

ChessMint (https://chessmint.ru) — онлайн-платформа для игры в шахматы, предоставляющая следующие функции:

- **Игра с живыми игроками** — создание партий с контролем времени (Bullet 1+0, Blitz 3+0/3+2/5+0/5+3, Rapid 10+0/10+5/15+10, Classical 30+0).
- **Поиск соперника (Matchmaking)** — автоматический подбор противника по рейтингу из очереди.
- **Игра с другом** — создание приглашения по ссылке/QR-коду без необходимости регистрации.
- **Игра с компьютером** — партии против шахматного движка с настраиваемой силой (ELO от 1350 до 2800). Пользователь выбирает цвет (белые, чёрные, случайно) и уровень сложности через ползунок. Ход компьютера рассчитывается на сервере и приходит через WebSocket в реальном времени. Играть можно без регистрации.
- **Шахматные задачи (Puzzles)** — тренировка тактики с несколькими режимами:
  - *Марафон* — задачи от рейтинга ~1000 с нарастающей сложностью, доступен без регистрации.
  - *Выживание* — случайные задачи разной сложности, серия прерывается при ошибке (требуется авторизация).
  - *Рейтинговый режим* — задачи, подобранные под рейтинг пользователя с ELO-системой (требуется авторизация).
  - *Ежедневная задача* — одна задача в день, одинаковая для всех пользователей.
  - Для каждой задачи отображаются темы (тактические мотивы), дебютные теги, популярность и статистика решений.
- **Рейтинговая система** — ELO-рейтинг по форматам (Bullet, Blitz, Rapid) для игр и отдельный рейтинг для задач, таблица лидеров.
- **Зал ожидания (Lobby)** — просмотр открытых партий, фильтрация по типу (рейтинговые/товарищеские).
- **TV-режим** — наблюдение за текущими партиями в реальном времени.
- **Анонимный доступ** — возможность играть без регистрации (с ограничениями).

**Основные внешние особенности:**

- Высокая отзывчивость интерфейса: ходы в партии с живым соперником и ответы компьютера отображаются мгновенно через WebSocket.
- Поддержка мобильных устройств — адаптивный интерфейс для всех разделов (игры, задачи, профиль).
- Переключение между светлой и тёмной темой.
- Мгновенная синхронизация состояния партии при переподключении.
- Отсутствие необходимости установки приложений — работа полностью в браузере.
- Автоматический таймаут неактивных партий.
- Задачи подаются из кэша — ответ на запрос случайной задачи приходит практически мгновенно, что свидетельствует о механизме предварительного кэширования.
- Ход компьютера генерируется на сервере (а не в браузере), что исключает возможность манипуляции AI на стороне клиента.

### 2. Анализ ограничений архитектуры

На основе внешних наблюдений за поведением платформы можно выделить следующие признаки возможных архитектурных ограничений:

**Производительность:**
- При одновременном открытии множества активных партий в TV-режиме наблюдается увеличение потребления ресурсов на стороне клиента, что свидетельствует об интенсивном использовании WebSocket-соединений.
- Время первоначальной загрузки страницы может быть выше оптимального из-за множества подключаемых JS-модулей (более 10 скриптов на странице `/games`, аналогично ~10 на странице `/tasks`).
- Ответ компьютера на ход игрока приходит с переменной задержкой (от долей секунды до нескольких секунд) в зависимости от уровня сложности. На высоких уровнях ожидание заметно дольше, что указывает на серверный расчёт хода с ограничением по глубине/времени.

**Масштабируемость:**
- Система matchmaking предполагает наличие очереди для подбора соперника. При малом количестве онлайн-игроков время ожидания может быть неопределённо долгим, что указывает на отсутствие механизма расширения допустимого рейтингового диапазона с течением времени.
- Анонимные пользователи не могут участвовать в matchmaking — только в играх по ссылке. Это ограничивает пул доступных соперников.
- Шахматный движок для игры с компьютером работает на том же сервере, что и остальные сервисы. При большом количестве одновременных партий с AI нагрузка на CPU может стать критической, так как шахматные движки интенсивно используют вычислительные ресурсы.
- Задачи выдаются из кэша — при истечении кэша или при его инвалидации возможна кратковременная задержка ответа, пока кэш не заполнится заново из БД.

**Безопасность:**
- Система использует JWT-токены для аутентификации (видно из заголовков Authorization в сетевых запросах). Для анонимных пользователей используется отдельный идентификатор сессии.
- WebSocket-соединения (для партий, matchmaking, игры с компьютером) требуют передачи токена в параметрах URL, что потенциально менее безопасно, чем передача через заголовки (токен может появиться в логах сервера).
- При решении задач валидация правильности хода происходит на стороне сервера — клиент отправляет только попытку, что исключает подделку результата.

**Устойчивость:**
- При разрыве WebSocket-соединения (закрытие вкладки, потеря сети) игрок автоматически удаляется из очереди matchmaking, что предотвращает «зависание» в поиске.
- Однако при разрыве соединения во время активной партии с живым соперником или компьютером механизм переподключения зависит от клиентской стороны — серверная сторона, вероятно, не сохраняет состояние WebSocket-сессии.
- Партии с компьютером не имеют контроля времени (режим «unlimited»), поэтому незавершённая партия при закрытии браузера сохраняется в БД, но механизм её автоматического завершения извне не наблюдается.

**Функциональные ограничения:**
- Функция сдачи (resign) в партии с компьютером отображается в интерфейсе, но при нажатии ничего не происходит — вероятно, функциональность на backend не реализована.
- В марафонном режиме задач статистика решений не сохраняется для неавторизованных пользователей — результат виден только в текущей сессии.
- Ежедневная задача допускает только одну попытку в сутки: при повторном решении сервер возвращает ошибку 409, но пользовательский интерфейс не всегда корректно это обрабатывает.

### 3. Гипотеза внутреннего устройства

На основе внешнего анализа можно выдвинуть следующие предположения об архитектуре ChessMint:

**Тип архитектуры: микросервисная с элементами клиент-серверной**

Основания для этого вывода:

1. **Независимость подсистем.** Шахматные задачи, игры с живыми игроками, игры с компьютером и система аутентификации работают независимо друг от друга — сбой одного модуля не влияет на другие. Это характерно для микросервисной архитектуры.

2. **Различные API-маршруты.** Наблюдение за сетевыми запросами показывает чётко разграниченные API-пути: `/api/games/`, `/api/puzzles/`, `/api/auth/`, `/api/computer-games/`, `/api/matchmaking/`. Каждая группа, вероятно, обслуживается отдельным сервисом.

3. **Наличие API-шлюза.** Все запросы идут на один домен, но перенаправляются к разным backend-сервисам по путям. Это указывает на использование обратного прокси (вероятно, Nginx) в качестве API-шлюза.

4. **WebSocket-эндпоинты.** Отдельные WebSocket-подключения для игр (`/ws/games/:id`), компьютерных партий (`/ws/computer-games/:id`), статистики онлайна (`/ws/stats`) и matchmaking (`/ws/matchmaking`) свидетельствуют о разделении реального времени на несколько независимых каналов, обслуживаемых разными сервисами.

5. **Контейнеризация.** Заголовки ответов и особенности развёртывания указывают на использование Docker-контейнеров, что является стандартным подходом для микросервисной архитектуры.

6. **Использование различных технологий.** Судя по характеристикам ответов API (скорость, формат ошибок), разные сервисы могут быть реализованы на разных языках/фреймворках — вероятно, комбинация Python и Go, что является распространённым подходом для микросервисов.

7. **Серверная генерация ходов AI.** Ход компьютера рассчитывается на сервере, а не в браузере. Это указывает на встроенный шахматный движок (вероятно, Stockfish) внутри сервиса компьютерных партий, взаимодействие с которым идёт через стандартный UCI-протокол.

8. **Кэширование задач.** Ответы на запросы случайных задач приходят быстрее, чем можно ожидать от прямого запроса к БД (где хранятся миллионы позиций). Это указывает на наличие in-memory кэша задач на стороне сервера с предварительной загрузкой и периодическим обновлением.

**Предполагаемая схема компонентов:**

```
┌─────────────────────────────────────────────────────────────────┐
│                       Клиент (Браузер)                          │
│  HTML/CSS/JS · REST API · WebSocket (игры, AI, matchmaking)     │
└──────────────────────┬──────────────┬──────────────────────────┘
                       │              │
              ┌────────▼──────────────▼─────────┐
              │      API-шлюз (Nginx Proxy)     │
              │    Маршрутизация · SSL · Gzip   │
              └──┬───────┬───────┬───────┬──────┘
                 │       │       │       │
           ┌─────▼──┐ ┌─▼────┐ ┌▼─────┐ ┌▼────────────┐
           │ Auth   │ │Games │ │Puz-  │ │ Computer    │
           │ Svc    │ │ Svc  │ │zles  │ │ Games Svc   │
           │(Python)│ │ (Go) │ │Svc   │ │ (Go)        │
           │FastAPI │ │ Gin  │ │(Py)  │ │  Gin        │
           └──┬─────┘ └──┬───┘ └─┬────┘ └──┬──────────┘
              │          │       │         │   ↕ UCI
              │          │       │         │ [Stockfish]
              │          │       │   ┌─────┘
              │    ┌─────▼───────▼───▼───┐
              │    │  PostgreSQL (общая)  │
              │    └─────────────────────┘
              │          │
              │    ┌─────▼──────────────┐
              │    │  Redis             │
              │    │  (matchmaking      │
              │    │   queue)           │
              │    └────────────────────┘
              │
         ┌────▼─────────────────────┐
         │  Мониторинг              │
         │  Prometheus · Grafana    │
         └──────────────────────────┘
```

**Предполагаемые технологии:**
- **Backend:** Python (FastAPI) для сервисов аутентификации и задач; Go (Gin) для игрового сервиса и сервиса компьютерных партий (требуют низкую латентность WebSocket и эффективное управление UCI-процессами).
- **Шахматный движок:** Stockfish — взаимодействие через UCI-протокол на серверной стороне; 21 уровень сложности (ELO ~1350–2800).
- **База данных:** PostgreSQL — единая для всех сервисов (судя по согласованности данных между профилем, рейтингами, историей партий и статистикой задач).
- **Кэширование:** In-memory кэш задач на стороне Python-сервиса (предзагрузка с TTL); Redis — для matchmaking-очереди (отсортированная структура по рейтингу).
- **API-шлюз:** Nginx — обратный прокси с маршрутизацией по пути.
- **Контейнеризация:** Docker, Docker Compose.
- **Мониторинг:** Prometheus + Grafana (стандартный стек для микросервисов).

### 4. Оценка качества архитектуры по критериям

#### 4.1 Функциональные критерии

| Критерий | Оценка | Обоснование |
|----------|--------|-------------|
| Соответствие бизнес-целям | **Высокая** | Платформа полностью покрывает основные сценарии: игра с людьми, с компьютером (21 уровень сложности), тренировка задачами (4 режима), рейтинговая система. |
| Поддерживаемость функций | **Высокая** | Микросервисная архитектура позволяет добавлять новые модули (matchmaking, новые режимы задач) без изменения существующих. |
| Масштабируемость | **Средняя** | Горизонтальное масштабирование возможно для отдельных сервисов, но единая БД и серверный шахматный движок (CPU-интенсивный) могут стать узкими местами при росте нагрузки. |
| Производительность | **Высокая** | Использование Go для игрового сервиса и AI-сервиса обеспечивает низкую латентность; WebSocket — мгновенная синхронизация ходов. Кэширование задач — быстрая выдача без обращения к БД. |
| Безопасность | **Средняя** | JWT-аутентификация, серверная валидация ходов в задачах и партиях. Но передача токена в URL для WebSocket — потенциальный риск. |

#### 4.2 Качественные характеристики

| Критерий | Оценка | Обоснование |
|----------|--------|-------------|
| Надёжность | **Средняя** | Автоматическое удаление из очереди при disconnect — хорошо. Серверный AI исключает сбои клиента. Но отсутствие видимых механизмов graceful degradation при падении отдельных сервисов. |
| Устойчивость к изменениям | **Высокая** | Микросервисы позволяют менять один модуль без влияния на остальные. Добавление новых режимов задач или уровней AI не требует переработки ядра системы. |
| Тестируемость | **Средняя** | Отсутствие интерфейсов между слоями (прямые зависимости на конкретные структуры) усложняет unit-тестирование. Сервис задач и AI-сервис тестируются изолированно. |
| Совместимость | **Высокая** | REST API + WebSocket — стандартные протоколы, лёгкая интеграция с любым клиентом. UCI-интерфейс для шахматного движка — стандарт индустрии. |
| Портативность | **Высокая** | Docker-контейнеризация обеспечивает развёртывание на любой платформе. Stockfish — кроссплатформенный. |

#### 4.3 Организационные и экономические критерии

| Критерий | Оценка | Обоснование |
|----------|--------|-------------|
| Стоимость владения | **Низкая** | Открытые технологии (PostgreSQL, Redis, Nginx), минимальная инфраструктура — один сервер. |
| Простота эксплуатации | **Средняя** | Docker Compose упрощает развёртывание, но множество сервисов требует мониторинга каждого. |
| Энергоэффективность | **Высокая** | Go-сервис потребляет значительно меньше ресурсов, чем аналог на Python, для real-time задач. |

| Критерий | Оценка | Обоснование |

### 5. Выявленные риски

1. **Единая база данных.** Все микросервисы, предположительно, работают с одной PostgreSQL. При росте нагрузки это станет узким местом и нарушает принцип изоляции данных в микросервисной архитектуре.

2. **Отсутствие брокера сообщений.** Взаимодействие между сервисами, вероятно, происходит через прямые HTTP-вызовы, а не через очередь сообщений. Это создаёт жёсткую связность и снижает отказоустойчивость.

3. **Передача JWT в URL.** Для WebSocket-подключений токен передаётся как query-параметр, что может привести к его утечке через логи, историю браузера или реферер.

4. **Отсутствие CDN.** Статические ресурсы (CSS, JS, изображения), вероятно, раздаются тем же сервером, что и API. При росте аудитории это повлияет на производительность.

5. **Matchmaking при малом онлайне.** Текущая реализация подбирает ближайшего по рейтингу, но не учитывает время ожидания. Два игрока с большой разницей в рейтинге всегда будут сведены, что может ухудшить игровой опыт.

6. **Нагрузка от шахматного движка.** Stockfish — CPU-интенсивный процесс. Каждая активная партия с компьютером занимает ресурсы сервера на расчёт хода. При большом количестве одновременных AI-партий сервер может исчерпать вычислительные ресурсы, что повлияет и на другие сервисы.

7. **In-memory кэш задач.** Кэш задач хранится в памяти Python-процесса. При перезапуске сервиса кэш теряется, и до его повторного наполнения возможна повышенная нагрузка на БД. Также объём кэша ограничен оперативной памятью контейнера.

8. **Незавершённые функции.** Функция сдачи партии с компьютером (resign) отображается в интерфейсе, но не реализована на backend. Это создаёт негативный пользовательский опыт и свидетельствует о незавершённости отдельных модулей.

### 6. Предлагаемые мероприятия по улучшению

На основе проведённого анализа рекомендуется рассмотреть следующие направления развития:

1. **Разделение базы данных.** Перевести каждый микросервис на собственную схему или отдельный экземпляр БД для обеспечения изоляции данных и независимого масштабирования. Это соответствует паттерну «Database per Service».

2. **Внедрение брокера сообщений.** Добавить Apache Kafka или RabbitMQ для асинхронной коммуникации между сервисами (например, обновление рейтинга после партии, уведомления). Это повысит отказоустойчивость и развяжет зависимости.

3. **Улучшение безопасности WebSocket.** Реализовать механизм одноразовых токенов (ticket-based authentication): клиент получает короткоживущий ticket через REST API и использует его для установки WebSocket-соединения, после чего ticket становится недействительным.

4. **Подключение CDN.** Разместить статические ресурсы на CDN (CloudFlare, Selectel CDN) для снижения нагрузки на основной сервер и ускорения загрузки для пользователей из разных регионов.

5. **Улучшение matchmaking.** Реализовать расширяющийся диапазон рейтинга: начинать поиск среди ±100 ELO и постепенно расширять диапазон каждые 5–10 секунд ожидания. Это обеспечит баланс между скоростью поиска и качеством подбора.

6. **Внедрение Circuit Breaker.** Добавить паттерн автоматического размыкателя для межсервисных вызовов, чтобы сбой одного сервиса не приводил к каскадным отказам.

7. **Бандлинг JS-модулей.** Объединить множество отдельных JS-файлов (>10 на странице) в один или несколько бандлов с помощью Webpack/Vite для уменьшения количества HTTP-запросов и ускорения загрузки страницы.

8. **Вынос шахматного движка в отдельный сервис.** Изолировать Stockfish в отдельный контейнер/микросервис с собственным лимитом ресурсов. Это позволит масштабировать AI-нагрузку независимо от остальных сервисов и предотвратить влияние CPU-интенсивных расчётов на производительность игр с живыми соперниками и задач.

9. **Миграция кэша задач на Redis.** Перенести in-memory кэш задач из Python-процесса в Redis. Это обеспечит сохранение кэша при перезапуске сервиса, возможность совместного использования кэша несколькими инстансами, и контролируемое вытеснение данных через TTL/LRU-политики.

10. **Доработка функциональности AI-партий.** Реализовать функцию сдачи (resign) на backend для компьютерных партий. Добавить механизм автоматического завершения заброшенных AI-партий по таймауту неактивности.

## Заключение

Архитектура ChessMint представляет собой микросервисную систему с использованием API-шлюза, что обеспечивает высокую модульность, независимость компонентов и возможность применения различных технологий для разных задач (Go для real-time игр и AI-партий, Python для задач и аутентификации). Платформа покрывает все ключевые сценарии шахматной площадки: игры с живыми соперниками с автоматическим подбором, партии с компьютером на 21 уровне сложности (Stockfish), тренировку тактики через четыре режима задач с ELO-рейтингом, и ежедневную задачу.

Система демонстрирует высокую производительность в реальном времени благодаря WebSocket-соединениям для всех типов партий, серверному расчёту ходов AI через UCI-протокол и in-memory кэшированию задач для мгновенной выдачи.

Основные точки роста связаны с масштабируемостью (единая БД, CPU-интенсивный шахматный движок на общем сервере, in-memory кэш без персистенции), безопасностью (передача токенов через URL) и отказоустойчивостью (отсутствие брокера сообщений и Circuit Breaker). При текущем масштабе проекта эти ограничения не являются критическими, но должны быть учтены при планировании дальнейшего развития платформы.
